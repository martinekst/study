# Pricing discovery and work breakdown

## Establish the baseline

Before estimating, identify the exact deliverable/version, included outcomes,
excluded outcomes, acceptance boundary, supplied assets, integrations, data and
migration, security/compliance, operational expectations, environments, rollout,
and customer responsibilities. Link each answer to documentation or record it as
an assumption/open question.

Ask only questions that can change scope, effort, rate, sequencing, or risk. Do
not block the whole estimate on an unknown that affects one item; isolate that
item, show a range or spike, and state what closes the uncertainty.

## Decompose by deliverable

Start with customer-visible outcomes or independently purchasable milestones,
then decompose into the work needed to make each outcome usable. Consider, where
applicable:

- discovery/decision and UX/design;
- functional implementation across UI, services, data, and integrations;
- migration/content/configuration;
- security, performance, accessibility, localization, and operations;
- automated/manual testing, environments, release, training, and documentation;
- project/technical coordination and acceptance support.

Do not create a checklist item when the scope gives no reason for it. Conversely,
do not price only feature coding while silently omitting integration, rollout, or
quality work required by the stated acceptance boundary.

Each work item has one primary outcome, scope anchor, estimate unit/range, roles,
dependencies, assumption/exclusion, and uncertainty treatment. Avoid duplicate
work across milestones; identify shared foundations once and show which options
reuse them.

## Variants

Variants must be comparable on the same price, tax, timing, quality, and support
basis. State the decision each variant represents, not just “small/medium/large”.
Make shared scope and incremental scope visible. A cheaper option must show what
outcome, quality, risk treatment, or timing is different.
