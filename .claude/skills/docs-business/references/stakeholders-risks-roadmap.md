# Stakeholders, risks, and roadmap

## Stakeholder decisions

A stakeholder is a role, team, person, partner, regulator, or affected customer
whose decision, work, or outcome changes. Capture only the fields useful to the
engagement:

| Field              | Purpose                                                            |
| ------------------ | ------------------------------------------------------------------ |
| Stakeholder        | concrete role/team/person supported by evidence                    |
| Interest/outcome   | what success or harm means from this perspective                   |
| Influence          | evidenced decision or veto power, not seniority guessed from title |
| Impact             | how substantially work or results change                           |
| Input required     | decision, data, time, approval, or operational change needed       |
| Commitment to them | output, training, evidence, transition, or communication owed      |

For decision matrices prefer plain responsibilities such as `Decides`,
`Provides`, and `Uses/Receives`. Put the legend immediately below the matrix and
explain only terms actually present. Do not silently assign an owner. An implied
but unnamed stakeholder is marked as an inference and remains an open question.

## Risks and assumptions

Give each material item a stable local ID. Keep risks, assumptions, constraints,
dependencies, and exclusions distinct.

| Field                 | Required content                                                        |
| --------------------- | ----------------------------------------------------------------------- |
| Risk                  | uncertain event or condition and its consequence                        |
| Evidence/trigger      | why it is credible and what would show it is occurring                  |
| Likelihood/impact     | supported qualitative level; use `unknown` when unsupported             |
| Treatment             | avoid, reduce, transfer, accept, or investigate, with a concrete action |
| Decision owner        | only when an authoritative owner is known                               |
| Dependency/assumption | condition on which the treatment or plan relies                         |

Use color only together with words. Do not calculate a numeric risk score unless
the source organization already uses a defined scale.

## Outcome roadmap

Roadmap milestones describe usable outcomes or decisions, not activity labels.
For each milestone state the outcome, entry evidence, exit/acceptance evidence,
dependencies, external gate, and timing confidence. Keep target dates separate
from committed dates. If only sequence is known, show sequence without inventing
a calendar.

A roadmap is not a replacement for detailed change requests or a live project
plan. Link to those sources when they exist.
